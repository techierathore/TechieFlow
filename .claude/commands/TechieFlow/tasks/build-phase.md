# build-phase

`*build-phase {App}` implements every open row of the phase's checklist, smoke-tests each screen it changed, chains the verifier, and repairs what the verifier fails. It runs to completion: YOLO is its default mode, and the pass ends only when every row on the working list is at least `Implemented` or genuinely `Blocked`. Never edit the BRD or the mockups here; a specification gap is logged, not fixed. Never edit the checklist by shell: the Write tool, so the guards can see it.

First: `bash .tfcore/utils/tf-phase.sh start build-phase {App}` prints the start time and marks the command running; a database migration is refused without that marker.

## Read

`docs/{App}-Coding-Standards.md` and the standard files it names; `docs/{App}-Architecture.md` for module boundaries; the phase's checklist and UIDesign with `docs/mockups/` (`appPhase` in `core-config.yaml` names the phase); the library references the rows need (`.trblazeui/TrBlazeUI-AI-Reference.md`, `.techierag/TechieRag-AI-Reference.md`; build once if one is absent).

## Steps

1. `bash .tfcore/utils/tf-build-list.sh {App} --prompts` prints the mode, the working list, the clusters and one sub-agent prompt per cluster. FIX means the verifier or a smoke failed rows: build only those. FRESH means every open row. NOTHING means run the status gate and stop. A row without an acceptance line is refused: fix the checklist first, then re-run.
2. Spawn every cluster in one turn, each with its printed prompt unchanged: `[trblazeui]` clusters through `/trblazeui`, `[techierag]` through `/techierag`, `[builder]` through the harness's builder sub-agent (`tf-builder` when registered, else the general one). Wait for all of them. A cluster that returns `PARTIAL` is re-spawned with its missing rows. Context pressure is a reason to delegate more, never to stop, and a working list is never shortened: "run build-phase again for the rest" is not an ending.
3. A row that cannot be built as written (no mockup, two rows that contradict, a behaviour the BRD plainly needed and never named): take the sensible reading, write it in the row's Remarks, keep building, and log the gap as a `miss` (`.tfcore/tasks/_metrics-emit-gate.md`) with `miss_class` `unspecified-gap` or `spec-contradiction`, `artifact` naming the document, `found_by` `agent-review`, `found_phase` `build-phase`. A library gap goes into `docs/{App}-<Library>-Feedback.md` (from `.tfcore/templates/v4custom/app-library-feedback-tmpl.md`, one file per library) and the row becomes `Blocked`; never a workaround.
4. `bash .tfcore/utils/tf-build.sh`: PASS, or FAIL with the real errors (fix them, fanning out by file when there are many), or NOT-RUN naming the rungs tried, which is a host problem and never a blocker. `bash .tfcore/utils/tf-build.sh test` runs the tests.
5. Smoke every changed screen as `.tfcore/tasks/_smoke-test-policy.md` says and write the result into each row: `Implemented` when the smoke passed, else `FAIL` or `PARTIAL` with a dated Remark. A failed smoke re-enters step 1 in FIX mode on those rows; never chain the verifier with a known failure.
6. Chain the verifier: execute `.tfcore/tasks/verify-phase.md` inline with scope `all`. Executing means its steps run here, boot to ledger; a smoke is not a verify, and `Verified` is written only by that run (the hook refuses it otherwise).
7. Rows the verifier left `FAIL` or `Needs re-verify` re-enter step 1 in FIX mode, up to five cycles, each cycle with its own run record (`"mode":"fix"`). A row still failing after five cycles stays `FAIL` with a Remark naming the cycle count and the last defect, and goes into PROJECT-STATUS "Known blockers". The only rows allowed below `Implemented` at the end of a pass are `Blocked` by a logged library gap or waiting on something only the owner has (credentials, a device, a paid account, a product decision), each named in "Known blockers".
8. Run the status gate (`.tfcore/tasks/_status-update-gate.md`). The run record carries `"cmd":"build-phase"`, `"mode":"build"` on a fresh pass or `"fix"` on a re-entry, `subagents` naming what was fanned out, and `build_result` as it was. In FIX mode, for every repaired row that had an open miss, append a `miss-fix` carrying the verifier's verdict (`bash .tfcore/utils/tf-emit.sh --open-miss REQ-…`, then `--next-fix-attempt`). When this pass is the last phase of a goal run, write the sentinel (`.tfcore/tasks/_yolo-mode.md`).
9. Report: mode, clusters and builders, rows implemented, rows blocked and why, library gaps logged, specification gaps logged, the build rung, the smoke run, the verifier's counts, and the next command from the gate.
