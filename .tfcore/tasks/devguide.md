# devguide

`*devguide {App} [scope] [--update]` writes the developer's map from each screen to the code that serves it: `docs/{App}-DevGuide.md` for phase 1, `docs/{App}-Pn-DevGuide.md` for a later phase, from `.tfcore/templates/v4custom/app-devguide-tmpl.md`. It documents the code as built, read at file and line, so a developer can set a breakpoint and find a bug. It never edits source. For a UI library the unit is the component; for a service library the unit is the public service; both are for the developer who maintains the library. Produced when the build completes the checklist, refreshed at handoff, and re-runnable with `--update` for changed screens only.

First: `bash .tfcore/utils/tf-phase.sh start devguide {App}` prints the start time and marks the command running.

## Steps

1. `bash .tfcore/utils/tf-devguide-list.sh {App} [--update]` prints the kind and the work list. For an app: every routed page found in the code with its file, its UIDesign screen and the roles that reach it; a screen the UIDesign names that has no code (a defect to log on its row); a route in the code with no UIDesign screen (document it, tell the analyst). For a UI library: every public component and the sample page that shows it. For a service library: every registration, interface and class and the sample that calls it. With `--update`: which entries have files newer than the guide's "Verified on" date; the rest are kept verbatim. NOTHING means there is no built code: say so and stop. A `{scope}` limits the list to the screens or roles named.
2. Fan out one sub-agent per group of screens (or components, or services), each with its lines from the list. Every entry is read at file and line, never inferred: the screenshot link, one "Call chain:" line from the page method to the service method to the data-access method, and the where-to-break table (file and line, the function, the variable to watch, the value it should hold). A route, a landing page or a menu target is read from the navigation code, never guessed from a folder or role name. A path that cannot be confirmed is written `{unresolved — reason}`, never invented. A control whose data cannot reach it (a guard that hides it, a column that does not map to the property, a required parameter never supplied) is a defect, not a working control.
3. Boot the application yourself (`bash .tfcore/utils/tf-build.sh run <head>`; a library boots its sample app; dependent services start first, in order, from their own configuration) and drive every screen with the verifier's render sweep (`.tfcore/tasks/verify-phase.md §4a`), signed in as each role's user from the UsageGuide. Save one screenshot per screen to `docs/screenshots/{App}/<role>-<screen>.png` (desktop width, and a mobile one when the layout is responsive) and link it from the entry. Write what was seen into each entry: renders, renders empty, error, unreachable. Only when the ladder's last rung has failed does the guide carry the banner `⚠ STATIC-ONLY — not runtime-verified` at the top and every entry `static-only (unconfirmed)`; a "renders" that was not seen is never written.
4. Every confirmed defect goes into the checklist: a dated Remark `⚠ DevGuide {date}: <defect> <file:line>` on the owning row, and `Needs re-verify` when the feature does not work as specified. Never `Verified`. An unresolved path gets a Remark only, no status change.
5. Show the screenshots to the owner and ask, screen by screen, what needs to change; log each answer on the owning row (`⚠ visual:` for layout) or as a miss. When nobody is present (a chained run), skip the questions and name the screenshots folder in the report.
6. Run the status gate (`.tfcore/tasks/_status-update-gate.md`) with `"cmd":"devguide"`; the guide is a human document and is rendered.
7. Report: the guide's file, runtime-verified as which roles or static-only and why, screens documented, unresolved paths, render and visual defects logged, the screenshots folder, owner-requested changes logged, and the next command from the gate.
