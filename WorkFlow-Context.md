## 1. What this repository is

This is a **customized TechieFlow v4 framework** for a **solo developer** (Claude Max) shipping a portfolio of ~8–10 .NET / Blazor / MAUI apps. It is NOT an application — it is the template that gets copied into each app to drive its development with AI agents. The owner optimizes for **speed-to-market over process purity**: a stripped, opinionated subset of TechieFlow tuned for one person + AI, not the full multi-role story-by-story TechieFlow flow.

The stack the apps target: **.NET 9 / Blazor (Server | WASM | Auto) / TrBlazeUI (UI library) / TechieRag (RAG/LLM library) / optional MAUI**. Claude Code runs inside **Windows WSL** — no GUI Playwright, MAUI builds/runs on the Windows side (see `WORKFLOW.html` §0, §11).

## 2. How the framework is used (the flow)

The canonical reference for humans is **`WORKFLOW.html`** (open in a browser). The short version for an agent:

1. **Scaffold** a new app by copying this template (`scaffold-greenfield.sh` / `scaffold-brownfield.sh`) — never `npm install`. `update-framework.sh` re-syncs an existing app to the latest framework.
2. **Day-1** (`*day1-greenfield` / `*day1-brownfield` on the **analyst**): produces Architecture, BRD, Coding-Standards, `.editorconfig`, PROJECT-STATUS, CLAUDE.md + the UsageGuide, all HTML-rendered. **Greenfield also** produces **UI mockups** (§3.6 — `*mockups`); **brownfield also** migrates any dev plan into the one checklist and generates the screen-by-screen **DevGuide** (§7.6, which now also captures a screenshot of every screen + runs an owner visual-review gate).
3. **`*mockups`** (analyst, greenfield only): reads the TrBlazeUI component catalog, then produces `docs/<APP>-UIDesign.md` (per-screen `region → TrBlazeUI control` map) + rendered `docs/mockups/*.html`. The build's visual contract + the verifier's visual baseline. Approved with the BRD + Architecture before build.
4. **`*split-brd`** (analyst): splits the rich BRD into the **ONE** checklist `<APP>-Checklist.md` — all `REQ-UI/FN/NFR/RAG-*` in a single Requirements Status table (the two-file model is gone; prefixes still route work).
5. **Build** (`*build-phase` on **flow-master**): the SINGLE unified build. Clusters every open REQ and **calls `/trblazeui` (REQ-UI-*, from the mockups) and `/techierag` (REQ-RAG-*) as sub-agents** while building FN/NFR itself; self-smokes (data + visual), then **chains the verifier automatically**. (`build-ui-phase`/`build-rag-phase`/`build-functional-phase` were dissolved — trblazeui/techierag are skills the parent agents call, not standalone phase commands.)
6. **Verify** (`verifier` / Vidur, `*verify ui|functional|all` — scopes filter the one checklist by prefix): autonomously boots the app, runs Playwright + dotnet tests, and applies BOTH the **data-render gate** (§4a — controls show their data) AND the **visual-truth gate** (§4b — no overlap/clip/off-viewport, screenshot inspected, diffed vs mockup). `Verified` requires acceptance + data + visual. Verdicts → the one checklist's **Requirements Status** table.
7. **Handoff** (`*handoff-phase` on flow-master): usage/testing doc, status → Handoff, HTML re-render, per-library feedback consolidation.
8. **`*fix-issues`** (flow-master, any time): the bug-fix front door — drop a folder of screenshots (+ optional description), it reproduces with Playwright, triages, fans the fix out to the right builder, re-smokes (data+visual) + re-verifies, updates the docs. This is "the verifier passed but the UI is broken — who do I call?": flow-master, not the analyst.
9. **`*triage-issues`** (flow-master, any time): the **analyze-only** sibling for human-found bugs (UAT / production) — screenshots folder and/or a written bug list in, **docs out**: reproduces + triages each issue, demotes regressed REQs to `Needs re-verify` (dated `⚠ UAT bug` remarks), appends new `Planned` bug REQ rows with acceptance, optionally re-verifies sibling features (`verify` arg → a real executed verify-phase), refreshes DevGuide known-issues + PROJECT-STATUS (next command = the `*fix-issues` pointer). **Never edits code, never spawns builders** — fixing is a separate owner decision.

### Non-negotiable conventions (an agent must honor)

- **Status gate** (`.tfcore/tasks/_status-update-gate.md`): every checklist/phase-executing agent MUST end by updating `PROJECT-STATUS.md`. A phase is done when status reflects reality, not when the build is green.
- **ONE checklist per app** = `docs/<APP>-Checklist.md`, holding all `REQ-UI/FN/NFR/RAG-*` in a single **Requirements Status** table (the single source of truth for per-REQ status). The two-file model (`-UI-Checklist` + `-Functional-Checklist`) is **retired** — prefixes still route work and scope `*verify`. **Never** create dated `docs/qa/*.md` or `docs/verify/*.md` files (banned).
- **"Verified" = acceptance + data-render + visual-truth.** A REQ is `Verified` only if its acceptance test passes, its controls actually render their data (verify-phase §4a), AND every screen it owns LOOKS right — no overlap/clip/off-viewport, screenshot-inspected, diffed vs the mockup where one exists (verify-phase §4b, the **visual-truth gate**). Data-present-but-blank and data-present-but-visually-broken both FAIL → `Needs re-verify`. The same two gates apply to every self-smoke (`_smoke-test-policy.md`). This is the fix for "the verifier passed but the running UI is completely broken."
- **HTML rendering is for HUMAN docs only.** BRD, Architecture, UsageGuide, **UIDesign/mockups**, **DevGuide**, PROJECT-STATUS render to `.html` (mockups are HTML by construction). **The checklist NEVER renders to HTML** — it is an AI-agent working document kept in markdown only. All human HTML uses the shared shell with the **light/dark theme toggle** (time-of-day default, remembered choice, warm off-white light).
- **File naming:** `<APP>` prefix on canonical docs (`<APP>-BRD.md`, `<APP>-Architecture.md`, `<APP>-Checklist.md`, `<APP>-UIDesign.md`, …); mockups under `docs/mockups/`, DevGuide screenshots under `docs/screenshots/<APP>/`. Superseded docs → `docs/OldDocs/`, never `-v2` suffixes.
- **Library feedback:** one file PER library — `docs/<APP>-TrBlazeUI-Feedback.md` (TR-NNN), `docs/<APP>-TechieRag-Feedback.md` (TR-RAG-NNN). Log gaps, work around, never silently swallow; never combine the files (separate teams).
- **Telemetry is emitted, never assembled by hand.** Every phase task ends by appending ONE `runs.jsonl` record through `.tfcore/utils/tf-emit.sh` (the status gate is the trigger, `_status-update-gate.md` item 10); `verify-phase` §6a appends one `gates.jsonl` record per REQ it graded, carrying the FIRST gate that failed; `triage-issues` §6a appends `gate:"escaped"` records, which is the only way escape rate becomes computable. **Telemetry has no veto** — a failed emit never blocks a write, fails a build, or changes a verdict, and is never worth retrying or reporting. **Never** write metrics into `PROJECT-STATUS.md` or any `*-Checklist.md` (the guard hooks block it, correctly), never edit a `.jsonl` stream, never emit free text or requirement prose into a record, and never invent a field absent from `.tfcore/telemetry/SCHEMA.md`. Doctrine: `.tfcore/tasks/_metrics-emit-gate.md`.
- **Coding standards** are per-project (`docs/<APP>-Coding-Standards.md`); the field-prefix decision is per-project (e.g. AppManager uses `obj`, AstroLyfe uses no prefix). `docs/AppManager-Coding-Standards.md` + `docs/AstroLyfe-Coding-Standards.md` in this repo are **reference SAMPLES** for agents, not live docs.
- **Build invocation ladder** (`.tfcore/templates/v4custom/build-invocation-ladder.md`): solution-scan first; MAUI/iOS/Android in the `.sln` → start rung #4; workload errors (`NETSDK1178`, `Microsoft.*.Sdk missing`) mean *wrong rung*, never "build failed".

## 4. Recovering an interrupted session (`*refresh-status`)

If a build/verify run dies mid-phase — lost internet, **revoked/changed model access**, killed terminal, crashed agent — the status gate never runs, so `PROJECT-STATUS.md` is stale or wrong. Do **not** trust it. Run:

```
/TechieFlow:agents:flow-master *refresh-status <APP>        # add `verify` to also re-verify ambiguous REQs
```

It rebuilds PROJECT-STATUS from **ground-truth evidence** (the checklist Requirements Status tables + what's actually in the working tree, including source-file modification times + a fresh `dotnet build`), **refreshes the BRD §4 Development status snapshot** from those same checklists (and inserts that section into a legacy BRD that predates it — the one BRD edit it's allowed; see §5's 2026-06-14 follow-up), writes a dated `## Recovery note`, and prints the exact command to resume with. **It never runs git** — git is manual in this framework (agents never commit; since 2026-07-02 the harness **denies** `git`/`gh` outright — settings.json deny + the `.tfcore/hooks/block-git.sh` PreToolUse hook), so recovery reconstructs from the tables + files-on-disk + build, never commit history. It never edits source. Task: `.tfcore/tasks/refresh-status.md`; documented in `WORKFLOW.html` §8a. This exists because of the AstroLyfe incident (2026-06-13): an experimental model lost access mid-development and left no usable status.

### 2026-08-11 — the `commits.jsonl` design was answered instead of fixed; the hook now reconciles from `pre-commit`, and `.gitattributes` pins LF

**The owner pushed back on the 2026-08-10 answer, and was right to.** That entry established that an empty `commits.jsonl` is the seeded-then-waiting state and closed the item as *by design*. The owner's reply: he codes the same repos on more than one machine, so *"since we are not checking it into repository it would be a pain for me to collect data from them"* — and *"I think this feature increases the friction in data collection."*

The previous answer was correct about the mechanism and wrong about the question. `docs/metrics/` **is** tracked, so nothing is literally unversioned. But the *data* still failed to arrive, for three reasons that only bite on a multi-machine setup, and all three came from the hook appending exactly one record:

- **The newest record is always uncommitted.** `post-commit` fires after the commit is sealed, so its line lands in the *next* commit. Stop working on that machine and it is never pushed at all. The tree is also never clean — commit, and the file is dirty again immediately, forever.
- **A clone with no hook records nothing, silently.** `.git/hooks/` is not part of the repository, so every clone needs its own. The four Mac clones here (`AppStudio`, `TrSetup`, `TrStudio`, `TechieRag`) have `.tfcore/` from 2026-07-11 but no `docs/metrics/` and no `post-commit` — they have simply never been refreshed since telemetry landed, and nothing anywhere said so.
- **Commits made on the other machine were invisible here**, and vice versa. Two half-histories, neither complete, and merging the files by hand is how an append-only log loses records.

**The fix: the hook reconciles instead of appends.** On every commit it now writes a record for **every** commit reachable from HEAD that the stream does not already carry, skipping on `sha` — the same operation as `--backfill-commits`, which it delegates to (`--limit 500 --quiet`), falling back to the old pure-bash single-record path only when `python3` is absent. So after a pull, the next commit on *any* machine backfills everything the other one did. `git log` is itself an append-only log that push/pull already replicates everywhere; the stream was only ever a projection of it, and now it is maintained as one.

**The git ban is untouched.** This is still the owner's own `git commit`, still nothing added to the commit being made, still no agent path near it. `pre-commit` + `git add` — the "obvious" fix for the lag — stays rejected for the same reason as before. Reconciling from the log gets the completeness without putting version control inside an automated path.

**Two supporting changes so the gap cannot hide again:**

- `tf-metrics.sh --report` now prints **`⚠ no post-commit hook in THIS clone of: <app>`** — a filesystem read, never a git call, so it stays agent-safe. `metrics-report.md` tells the agent to surface it in §5 "What is missing" and explicitly **not** to act on it (installing is a refresh; backfilling is git). This is the one telemetry gap the owner could not see by reading the files.
- `tf-emit.sh` accepts a **JSONL batch** on stdin, not just one object, and resolves `project_type`/`harness`/`app` once per batch. Before this, a first reconcile of 400 commits meant 400 bash+python startups inside `git commit`. Single-object and pretty-printed input behave exactly as before; a malformed line is dropped on its own and the rest of the batch still lands.

**The second reported issue — GitHub on Windows warning "This file uses 'LF' line endings, but Git is configured to convert them to 'CRLF' the next time the file is checked out."** Same root cause as the 2026-07-11 incident, one layer out: the **framework repo** pinned `* text=auto eol=lf` back then, but **app repos never got the same treatment**. TrSetup / TrStudio / TechieRag carry the stock Visual Studio `.gitattributes` (`* text=auto`, nothing else); AppStudio has none at all. `text=auto` normalizes the committed *blob* to LF and still lets `core.autocrlf=true` smudge the *working tree* to CRLF on checkout — file on disk and file Git will next write disagree, and Git says so. On a `.jsonl` appended to by machine that is worse than cosmetic: mixed line endings inside a log.

The 8d `.gitattributes` block in all three scripts (added 2026-08-10 with `merge=union` only) now manages four lines:

```
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
docs/metrics/*.jsonl text eol=lf merge=union
```

`eol=lf` pins the **working tree**, which is the half `text=auto` never covered. `*.bat`/`*.cmd` are pinned back to CRLF — the Windows command processor requires it. The telemetry line is named explicitly as well as covered by `*` because it has to carry `merge=union` anyway. **The owner's follow-up found the hole in the reconcile design — duplicate shas — and it is now closed.** Asked *"won't I miss the last line added to `commits.jsonl` when I pull on a different machine?"*, the answer is no: that line describes a commit, the commit itself is pushed, and the other machine's reconcile rebuilds the record from `git log`. But the question exposed the symmetric case nobody had traced. Machine A records commit `N` locally; if that line is not yet pushed when B pulls `N` and reconciles, **both machines now hold a genuine record of `N`**, and `merge=union` — whose entire purpose is to never drop a line — keeps both. `--backfill-commits` skipped duplicate shas, but **`analyse()` did not**, so `commits`, `active_days` and `commits_per_active_day` would have drifted upward exactly in the multi-machine case the day's work was meant to serve. Union merge and de-duplication are two halves of one trade and only one half had been built. New `dedupe_commits()` collapses commit records on `sha` **per repo** (two repos may legitimately share a short sha), the report prints how many it collapsed rather than silently correcting, and only `commits` needs it — `runs`/`gates`/`sessions` describe events that happen on one machine and cannot be independently reconstructed, so union merge has no way to manufacture a second copy. Verified against a stream with a planted duplicate (4 lines → 3 counted, note printed) and against all four live repos (no change). Documented in SCHEMA §5, README §17, and two new WORKFLOW §15 FAQ entries — including the practical wrinkle that `commits.jsonl` always carries one pending line, so git refuses to pull when that file also changed upstream: commit the one-line diff first.

**Then the owner named the thing the reconcile fix had not touched, and the hook moved to `pre-commit`.** *"The wrinkle you are saying is exactly the issue I am saying — when I commit, a new line is added to the file after commit."* Correct, and the advice that came with the earlier fix (*"commit the one-line diff first, then pull"*) was circular: committing to clear the pending line creates a commit whose record is then pending in turn. `post-commit` cannot put its line inside the commit it describes, so **the working tree was never clean, permanently, with no reachable state where it was** — and on a repo worked from two machines that also blocked `git pull` every time the file had changed upstream. The 2026-08-08 design called this "the one-commit lag" and filed it as a caveat. It was a defect wearing a caveat's label; the lag is one commit either way, but "your tree is never clean" is not a lag.

Offered three options (pre-commit + stage · untrack it as a derived cache · leave it), the owner chose **pre-commit + stage**, which keeps the stream in the repo — the thing he asked for at the start — while making the tree clean. New `.tfcore/telemetry/pre-commit` reconciles from the log exactly as before, then `git add`s the one file so records ship *inside* the commit. `post-commit` is deleted from the framework, and `install-metrics.sh` **removes** an installed one (identified by the template's marker, so a hook the owner wrote is never touched) — `rsync --delete` on `.tfcore/telemetry/` retires the deployed template copies on the next refresh.

**This reverses a documented decision, so the risk it was rejected over is bounded rather than waived.** DECISIONS.md §3 had explicitly rejected `pre-commit` + `git add` as "putting version control inside an automated path"; that entry is now revised in place with both halves of the reasoning rather than rewritten. The bounds: it stages **exactly one path** (`docs/metrics/commits.jsonl` — never a directory, never `-A`, so it cannot pull source into a commit); on a **partial commit** (`git commit -- <paths>`, detected via `GIT_INDEX_FILE`) it writes the record and does **not** stage, so it can never add a file to a commit deliberately scoped down; and **every path exits 0**, because a pre-commit hook exiting non-zero *aborts the commit* and telemetry has no veto. Everything it skips — merges (git runs `pre-merge-commit` instead), `--no-verify`, rebase, cherry-pick, partial commits — is picked up by the next ordinary commit's reconcile, so skipping is never losing. Constraint 1 is untouched: *agents* still never run git, `block-git.sh` is unchanged, no agent path reaches the hook. What actually moved is the narrower habit that the framework's own git usage stays read-only — which was never a stated constraint, only an artifact of the post-commit design. `install-metrics.sh` also **never replaces a pre-commit hook it did not write** (unlike the old post-commit path, which backed up and replaced): losing someone's lint gate to a telemetry install is a worse outcome than not collecting commit records, so it warns and tells you how to chain instead.

### 2026-08-10 (2) — §4c, the performance gate: speed becomes gradeable, but only against a budget someone declared

**Where this came from.** While clearing the artifact litter (entry below), the throwaway dirs turned out to contain a hand-written load harness (`loadharness.py`, `ab.sh`) an agent had built from scratch to grade TechieBlog's REQ-NFR-001. That is the tell: §4a proves the data is present, §4b proves the screen is usable, and **nothing covered speed** — a page rendering every control perfectly in nine seconds passed every gate the framework had. An agent needing to invent tooling mid-verify is a missing framework feature, not a clever agent.

**The design constraint that shaped everything: this gate must not cry wolf.** A perf number on a dev box — WSL→Windows networking, sibling build agents, tiered JIT — is noisy. A gate that fails REQs on noise teaches the owner to ignore verdicts, and that costs far more than the defects it would have caught. Every decision below follows from that:

- **It never invents a budget.** §4c grades a REQ **only** if its acceptance criteria carry a machine-read line: `perf-budget: <p50|p95|max> <ttfb|load> <= <N>ms [@ concurrency <N>]`. No line → the gate does not run, `perf` is omitted from `gates_run`, nothing is reported. A REQ whose prose says "should be fast" is explicitly **not** gradeable — the run flags it in §8 as needing a number in the BRD, and moves on. Picking a sensible-sounding threshold would be the framework inventing a requirement.
- **Three bands, and the middle one is the point.** ≤ budget → `PERF-OK`. > budget but ≤ budget × 1.25 → `PERF-MARGINAL`, a dated remark that **never blocks `Verified`**, so drift is visible before it is a failure. > budget × 1.25 → `PERF-FAIL` → `Needs re-verify`.
- **Four refusals to grade**, each producing `PERF-UNMEASURED` with the reason: Debug build (no steady-state JIT — not evidence), `weak` sample (<20 behind the p95), any error or non-200 during the run (contaminated distribution, and the failure belongs to `acceptance`), visibly contended host.
- **MAUI native heads are not perf-gated at all.** The harness speaks HTTP; an Appium screen has no URL, and launch/frame timing is a different discipline. Same doctrine as `⚠ STATIC-ONLY` — unmeasured is unmeasured, never passed.

**New file `.tfcore/utils/tf-perf.sh`** — sibling of `tf-emit.sh`, python3-only, no new dependency. Samples TTFB (time to the first body byte) and full load over a declared path set at graded concurrency; discards warm-up requests; reports **p95, never the mean**; emits a `per_path` breakdown so the slow page is identifiable rather than just the slow screen; flags `weak` under 20 samples; stamps `build_config` and a machine fingerprint. **It produces numbers and never a verdict** — it does not read budgets, touch a checklist, or emit telemetry. A measurement tool that also judges is one you cannot audit when a number looks wrong. Exit codes: 0 measured · 2 unreachable · 3 bad args. Verified end-to-end against a synthetic server with injected 10/50/250 ms delays: measured p95s tracked the injections, `per_path` isolated `/slow`, and all three bands plus all four refusals fired correctly.

**Telemetry — the part that needed the most care.** `gate` gained `perf` (execution order now `build` → `acceptance` → `render` → `visual` → `perf` → `standards`; first-failing-gate semantics unchanged, so a REQ already `VISUAL-FAIL` still records `visual`). `failure_class` gained `slow-ttfb` / `slow-load` — **naming the metric only; the measured milliseconds are never emitted**, because a latency figure is a property of one machine on one day and these streams are pooled across hosts and months.

The real hazard is subtler and is now handled in code, not just prose: **a gate added mid-stream is structurally understated in the raw distribution.** Every record written before 2026-08-10 had zero chance of recording `perf`, and most records after it still will not run the gate. A `Counter` over `gate` therefore says almost nothing about how good the perf gate is. New **SCHEMA §3.5** states the correct denominator — `failures with gate="perf" ÷ records with "perf" in gates_run` — and `tf-metrics.sh` now carries a `LATE_GATES` table and prints coverage beside the count (`perf gate: ran on N records, caught M -> X%`, or `not yet run on this data (gate added 2026-08-10)`), with an explicit line that the share in the distribution above is **not** that rate. This is the same reasoning as the live/backfilled provenance rule arriving by a different route: a gate that ran on 6 of 400 records did not fail to catch things, it was not asked. Verified against synthetic data covering both branches and re-checked against TechieBlog's real 127-record stream (no regression; `MIN_N = 3` honored).

**A design bug the first real test caught — and the rule that replaced it.** The gate's original precondition list said *"`errors > 0` or any `non_200` → `PERF-UNMEASURED`"*, reasoning that failures contaminate a latency sample. Running it against TechieBlog's REQ-NFR-001 at `@ concurrency 100` produced **321 of 500 requests timing out** — and the gate would have shrugged and recorded *not measured*. That is exactly backwards: **requests timing out under load IS the perf result**, and a budget written `@ concurrency 100` is precisely a claim that this does not happen. The blanket rule made the gate useless at the concurrency levels it exists for.

Replaced with a rate-based branch, since only the rate separates the two situations: **`error_rate` ≥ 0.10 with timeout/connection error kinds → `PERF-FAIL`, `failure_class:"timeout"`** (the app did not serve the declared concurrency; report the completed/attempted split and label the p95 as survivors-only); **0 < `error_rate` < 0.10 → `PERF-UNMEASURED`** (a handful of failures means the sample is contaminated, not that the app is overloaded); **any `non_200` → `PERF-UNMEASURED` regardless of rate** (a 404 is a wrong path set, a 5xx belongs to the `acceptance` gate — neither is a latency verdict). A load-shed run can be both `weak` and a genuine `PERF-FAIL`; the load-shed verdict wins, because it does not depend on the latency distribution being trustworthy. `tf-perf.sh` now emits `attempted` and `error_rate` so the branch is mechanical rather than eyeballed, and `failure_class` gained **`timeout`** (SCHEMA §3.3 + the §6 status-mapping table, which now has separate PERF-FAIL rows for *slow* and *load shed*).

### 2026-08-08 — Development telemetry: the framework now keeps the evidence it was already producing

**The problem.** Every `*verify` run applied four separately-named gates (acceptance, §4a data-render, §4b visual-truth, standards-grep) to individually-identified requirements and wrote verdicts into the one checklist's Requirements Status table, plus `docs/.last-verify.json` as a run ledger. Then the next run overwrote the ledger, the table was mutated in place, and the history was gone. The framework could not answer three basic questions about any project built with it: **first-pass rate**, **gate catch distribution**, **escape rate**. Implemented from `docs/TechieFlow-Telemetry-Runbook.md`.

**The data model.** Four append-only, schema-versioned JSONL streams per app repo, under **`docs/metrics/` — TRACKED by version control on purpose**, since this is the one thing the framework cannot reconstruct after the fact (verified: no pattern in either managed `.gitignore` block catches it, and all three scripts now assert that at deploy time):

- **`gates.jsonl` — the primary stream.** One record per REQ verdict per verify run. Its `gate` field is **the FIRST gate that failed** (`build` → `acceptance` → `render` → `visual` → `standards`, in execution order — recording a later one would inflate the visual gate's apparent catch rate), `null` on a pass, or **`escaped`** when `*triage-issues` logs a defect a human found after every gate passed it. That one field produces both the gate catch distribution and the escape rate. `attempt` is *derived* by counting prior live records (`tf-emit.sh --next-attempt`), never guessed.
- **`runs.jsonl`** — one per framework command run, carrying `mode` (`build` vs FIX — the rework metric), `reqs_touched` (IDs only), `files_written`, `duration_s`.
- **`sessions.jsonl`** — written by a `SessionEnd` hook (event name verified against the installed Claude Code 2.1.226, not assumed). Token counts only: transcripts carry no per-message cost, so `cost_usd` is `null` and "cost per verified REQ" is reported **in tokens** — a rate-card multiplication would be an estimate presented as a measurement.
- **`commits.jsonl`** — written by the **owner's own `post-commit` hook**. Known limitation documented everywhere it matters: post-commit fires after the commit is sealed, so its record rides in the *next* commit — metrics lag reality by one commit. NOT worked around with pre-commit + staging, because that would put version control inside an automated path.

**The provenance rule — enforced in code, not just prose.** Two separations, the same rule twice: (a) records not written at the moment of the event carry `backfilled:true` and never pool with live records; (b) records never pool across `project_type`. **No report may print a combined first-pass rate, gate catch distribution, or escape rate crossing either boundary — not as a merged figure, not as a "total" row, not as an "overall" summary line.** `tf-metrics.sh` has no code path that produces one, which is deliberate: the task must make the tempting number impossible, not merely forbidden. Backfilled data appears in an adjacent labelled column with a footnote naming the inferred fields. Additionally, **any REQ carrying backfilled history is excluded from the live first-pass rate** — its live `attempt` numbering restarts at 1, so counting it would import the guess. Commit-derived metrics are exempt from both separations (the commit log is a real append-only log, and commit volume is comparable across types). The reasoning, recorded because it will be questioned: a merged first-pass rate cannot be defended when someone asks how attempts were counted, since backfilled attempts are inferred from a mutable status table that never recorded them — and one indefensible figure contaminates every other number on the page.

**Backfill — know what the data is worth.** `--backfill-gates` parses existing `<APP>-Checklist.md` Requirements Status tables + dated Remarks (`⚠ visual:` / `⚠ render gate:` / `⚠ UAT bug` markers classify the gate; only the *classification* is stored, never the remark text). Every record carries `backfilled:true` and `inferred:[...]`. **`attempt` is inferred on all of them, always** — the status table is a mutated-in-place snapshot, so a REQ that failed three times then passed is indistinguishable from one that passed first try. Backfilled gate data is **context and volume, never evidence for a published rate**. `--backfill-commits` is different and genuinely reliable.

**Privacy.** Records carry IDs, counts, durations, verdicts and file paths *at most*. `failure_class` is a closed enum (`blank-data`/`zero-rows`/`overlap`/`clipped`/`offscreen`/`exception`/`assert-fail`/`naming`/`build-error`/`other`) precisely so no free text can leak; commit **subjects** are discarded on the spot and only a `feat|fix|docs|chore|refactor|test|build` prefix is kept. This framework runs on employer projects and the files are append-only — a leaked field is not something you fix later.

### 2026-06-17 — Mermaid diagrams STILL erroring — real root cause found (the 2026-06-14 fix was a misdiagnosis)
The owner reported that AstroLyfe's regenerated Architecture + BRD HTML **still** show the bomb-icon **"Syntax error in text — mermaid version 11.15.0"** on flowcharts, despite the 2026-06-14 "Mermaid authoring rules" work. - **Every diagram parses and renders fine in isolation** — quoted *and* unquoted labels, with literal `<br/>`. The 2026-06-14 belief that **unquoted special characters** broke flowcharts was **wrong**: I never reproduced the failure before declaring it fixed. Unquoted labels are not the cause.
- **Actual root cause: a bug in the HTML shell's own JavaScript.** The "copy buttons on every `<pre>`" loop ran `document.querySelectorAll('pre')` and `appendChild`ed a `<button>copy</button>` into **`pre.mermaid` too** — *before* `mermaid.initialize`. Mermaid reads the `<pre>`'s `textContent` as the diagram source, so `copy` got glued onto the diagram's last line. On a **flowchart** that corrupts a node/edge id → "Syntax error". On a **sequence diagram** the trailing `copy` lands in freeform message text → still valid. **That** is why "only flowcharts broke, sequence diagrams were fine" — the signature the 2026-06-14 entry misattributed to label quoting. Reproduced the exact error and the fix in a Chrome A/B (`pre` vs `pre:not(.mermaid)`).
- **Fix:** scoped the selector to **`document.querySelectorAll('pre:not(.mermaid)')`** in `html-render-shell.md` §7 (+ explanatory comment, + the §1 feature bullet). Mermaid blocks already get copy/export from their own `.diagram` toolbar. Template only — **not mirrored** (templates load by relative path; harness mirrors cover agents/tasks only).
- **Patched the already-generated AstroLyfe HTML in place** (the owner needs them working now, not after a re-render): `AstroLyfe-Architecture.html`, `AstroLyfe-BRD.html`, `AstroLyfe-Functional-Checklist.html`, `AstroLyfe-UI-Checklist.html` — same one-line selector change. Verified by re-rendering in headless Chrome: **0 "Syntax error", 8/8 Architecture + 7/7 BRD diagrams render as real SVGs.**
