## What the five script changes actually do

Think of it as five separate small machines, each of which was lying to you in a different way.

**1. The build list was hiding work (TF-019).** When you run `*build-phase`, a script prints the list of requirements to build. If any row was broken, it printed *only* the broken ones. TfLens had two rows that can never be fixed (they need data that doesn't exist yet), so that script printed the same two rows forever — and twelve brand-new requirements were never printed at all. A pass could have finished, reported success, and left twelve requirements untouched. Now the list is every unfinished row, with the broken ones first, and it checks its own arithmetic: every row must be counted somewhere.

**2. A skipped test was being called a failure (TF-022).** Tests can say "skip me, there's no data for this yet." The script counted that the same as "this test failed." So two TfLens rows said FAIL when nothing was wrong — and a FAIL sends the builder back to re-fix them, up to five times, against a problem no code can solve. Now there are three answers instead of two: passed, failed, and *not measured*. A row whose tests were all skipped is marked "not tested" — it never counts as done, and it never counts as broken.

**3. The screen checker was measuring the wrong rectangle (TF-021, first half).** A wide table inside a box that scrolls sideways is 1167 pixels wide, but only 492 pixels of it are visible. The checker measured the full 1167, decided the table stretched across the card next to it, and reported "these two overlap." Nothing overlapped. Now it measures what's actually drawn on screen, not what the layout says on paper.

**4. It was also looking too early (TF-021, second half).** Blazor screens paint a moment after the page loads. The checker looked before that, saw an empty page, and reported every control as missing — while its own screenshot showed them all there. Now it waits up to five seconds for the screen to appear, then measures. If nothing appears, it still reports it missing, so a real fault is still caught.

**5. Two smaller ones (TF-018, TF-020)** were already fixed this morning; I re-proved them rather than touching them. One lets you correct a miss's description later. The other stops the framework's own scores being mixed into your app's scores, which was quietly flattering your app's numbers.

The important part: for each of these I first rebuilt the exact broken situation and confirmed the old script got it wrong, then confirmed the new one gets it right. And I added the opposite tests too — a screen that *really* does overlap, a control that *really* is missing, a test that *really* failed — so the fixes can't buy quiet by going blind.

## Q1 — nothing skips it. Here's the actual lifecycle, tested

I built a fixture and ran it rather than reasoning about it. A row whose tests were all skipped:

| Stage | What happens |
|---|---|
| Builder | **Does not skip it.** `Implemented` is not a terminal status, so the row is in the build list every pass: `Mode: FRESH — 1 row(s) to build … REQ-UI-034` |
| Verifier | **Does not skip the row.** Six of the seven checks still grade it — build, render, assets, visual, mockup, speed. Only *acceptance* can't run, because the test itself declined |
| Result | Status stays `Implemented`, percentage stays 60, and the remark says exactly why: *"not verified — every test named REQ-UI-034 was skipped; acceptance not measured (1 test skipped, none ran)"* |

So the functionality gets built normally. What can't happen is *proving* it works, because the data to prove it doesn't exist in that environment. The old behaviour called that a defect (FAIL), which sent the builder back to re-fix working code up to five times — that was the bug.
