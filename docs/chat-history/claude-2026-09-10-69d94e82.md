## 1. What happens when a model's limit is reached

Before: routing named one model per tier and the supervisor's only answer to a limit was to sleep until the reset.

Now each tier has a **second choice, and a third if you list one**, in `.tfcore/routing.yaml`:

```yaml
fallbacks:
  standard:
    claude: haiku
    opencode: opencode-go/mimo-v2.5, openai/gpt-5.6-luna
```

When a limit is hit, the supervisor parks that model until the reset time the message stated, asks the tier for the next model that isn't parked, **re-binds so the sub-agents move with it**, and starts the next cycle immediately. Only when every model in the chain is parked does it sleep, exactly as before. The same now happens on the silent OpenCode provider refusal that used to exit 5 on 2026-09-06.

The park record lives in `~/.techieflow/model-cooldown.json` — per machine, not per project, because a usage limit belongs to your account, so one project hitting a weekly limit stops the next project walking into it.

```bash
bash .tfcore/utils/tf-model-pick.sh status              # what every tier would run right now
bash .tfcore/utils/tf-model-pick.sh chain standard opencode
bash .tfcore/utils/tf-goal.sh --no-fallback ...         # turn it off, keep the old behaviour
```

**Where it will not help, said plainly:** on Claude Code the 5-hour and weekly limits belong to the account, not the model, so Sonnet → Haiku usually hits the same wall. The supervisor finds that out honestly — parks that one too, and after one wasted cycle waits as it always did. It earns its keep on a per-model limit (Opus out while the account is fine) and on OpenCode, where a monthly balance really is one provider's problem.
