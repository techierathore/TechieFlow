# Coupling Points — where TechieFlow depends on Claude Code behaviour

**Date:** 2026-08-19 · **Scope:** Task 2 · **Companion:** `Capability-Matrix.md` (the facts), `Adapter-Design.md` (what to do about the *breaks* items).

Ordered by severity. **breaks** = a phase cannot complete, or a hard framework rule the prose claims is mechanical is in fact unenforced; **degrades** = works but worse (lost guardrail, lost context, wrong next-command, lost telemetry); **cosmetic** = wording. Every row gives file:line in this repo (the Claude mirror `.claude/commands/TechieFlow/` is byte-identical to `.tfcore/`, so the same line numbers apply there). "OpenCode instead" cites `Capability-Matrix.md` rows or OpenCode source.

This list credits what the 2026-08-13 audit already fixed (`docs/TechieFlow-OpenCode-Gaps.md` GAPs 1–8 — mirror removed, `permission.bash` deny, `trblazeui`/`techierag` registered as agents, AGENTS.md instruction, dual-form invocation strings, `@` sigil note). Those are **not** repeated as open items; only what is still coupled is.

## 0. Shortest path to a working run in both harnesses

These six items are the whole critical path. Everything after §1 is inventory.

| Step | Item | Why it is on the critical path | Owner of the fix |
|---|---|---|---|
| 1 | **Run OpenCode in WSL, not Docker** (E-1) | Every runtime rung the framework relies on (`cmd.exe`/`winrun` via interop, headless Playwright libs, Appium on `localhost`) exists in the WSL distro and not in the container; the Docker path needed an SSH bridge, a second NuGet config, a second data dir and a key-permission workaround, and still cannot reach the Windows host like WSL can. OpenCode's own docs recommend WSL. | `OpenCode-Deployment-Guide.md` |
| 2 | **Make `update-framework.sh` refresh the framework-owned part of `opencode.jsonc`** (D-1) | Today the script *preserves* `opencode.jsonc`, so none of the 2026-08-13 fixes (git deny, library agents, AGENTS.md instruction, operating contract) reach an already-scaffolded app. Under OpenCode, `*build-phase` in those apps cannot spawn `trblazeui`/`techierag` (the `task` tool needs registered agents). | Adapter-Design §2 (managed block, same pattern as `.claude/settings.json`) |
| 3 | **Ship the guard hooks to OpenCode through a local plugin** (H-1, H-2) | `guard-verify.sh` (no `Verified` without a run ledger) and `guard-status.sh` (PROJECT-STATUS shape) are the two mechanical gates the prose promises; under OpenCode they do not run, so `gates.jsonl` can contain a self-attested `Verified` indistinguishable from an earned one. A `.opencode/plugin/techieflow.ts` loads without npm install (Matrix Q5) and can call the *existing* scripts. | Adapter-Design §2 |
| 4 | **Neutralise subagent vocabulary in three task files** (S-1) | `build-phase.md:65`, `verify-phase.md:166`, `fix-issues.md:49` name Claude's `Agent` tool and `general-purpose` agent; OpenCode's are `task` and `general`. Agents usually adapt, but the fan-out is "MANDATORY — do not skip" and a wrong tool name is the most common place a run stalls. | Adapter-Design §3 (vocabulary table, no logic change) |
| 5 | **Give OpenCode the standards layer** (C-1) | OpenCode never loads `CLAUDE.md`; the day-1 `AGENTS.md` is a *pointer* the agent may or may not follow; coding-standards drift is the observed result. | Adapter-Design §3 |
| 6 | **Verify, then retire, the "compound git forms are not matched" belief** (H-3) | OpenCode parses bash with tree-sitter and evaluates each command node; the repo's comment and prose say otherwise. If the source is right, the git ban is already mechanical under OpenCode and two paragraphs of hedging can go. If it is wrong, the plugin from step 3 adds the compound guard for free. | 1-minute runtime test, then Adapter-Design §2 |

## 5. Explicit answers the design needs

- **Does any telemetry record carry model/tokens today?** Only `sessions.jsonl` (Claude only): `session_id, model, duration_s, input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, cost_usd(null)`. `runs.jsonl` and `gates.jsonl` carry neither (`SCHEMA.md:78-127`).
- **How are tokens obtained on Claude?** `metrics-session.sh:59-82` sums `message.usage.*` over `type=="assistant"` lines of the transcript at `transcript_path` from the `SessionEnd` payload; model = last `message.model`.
- **How is `harness` detected?** `tf-emit.sh:192-225` (env → process walk → `null`).
- **Where do tasks spawn subagents?** `build-phase.md:62-77,89,100,119`; `fix-issues.md:47-51,94`; `verify-phase.md:142,166,173,186`; `devguide.md:58,84-86,102,203`; `productguide.md:41`; `mockups.md:38`; `triage-issues.md:20,120,134` (the *negative* — must not spawn). Claude tool names appear only at `build-phase.md:65` and `verify-phase.md:166`.
- **Any model/thinking mentions?** None in any task/agent file. No `ultrathink`, `/model`, `opus/sonnet/haiku` anywhere in `.tfcore`, `.claude`, `.opencode`, the scripts, README or WORKFLOW.html.

## Council of experts — adversarial review

- **Framework owner:** "You call E-1 'breaks' but the Docker path was deliberately built and documented over three days." — *Yes, and that is the tell:* three days of bridge work to recover capabilities the WSL distro already had. The coupling is not to Claude Code; it is to *the Linux-on-Windows runtime shape* that Claude Code happened to be run in. Moving OpenCode into the same shape removes a whole class of coupling at zero framework cost. The Docker artefacts stay on disk as a fallback.
- **Red team:** "H-1/H-2 under OpenCode: the agent still *reads* the rule in prose; is it really 'breaks'?" — The 2026-07-09 incident (self-attested `Verified` despite prose) is why the hook exists. A rule the prose calls mechanical but isn't is worse than no rule: downstream data (`gates.jsonl`) is trusted on the strength of it. Severity stands.
- **OpenCode maintainer:** "S-1 — agents are robust to tool-name drift; they see the real tool list." — Usually. But `build-phase` makes the fan-out *mandatory* and threatens the agent with "banned anti-pattern" for doing it sequentially; a model that cannot find `Agent`/`general-purpose` tends to do exactly the banned thing and narrate why. A three-line vocabulary fix is cheaper than one stalled build.
- **Data sceptic:** "T-2 — process-walk detection works today; why list it?" — Because `harness` is the one field every per-harness comparison keys on, and it currently depends on the binary being named `opencode` and on `/proc` being readable. The adapter can set one env var at the harness boundary and make it a fact instead of an inference.
- **Minimalist:** "Most of §3 should not be in this doc." — Agreed that it is not on the critical path; it is here so nobody re-inventories. §0 is the deliverable.
